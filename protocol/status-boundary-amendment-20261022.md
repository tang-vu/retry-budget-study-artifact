# Application status boundary extension

Owner authorization: complete the recommended retry manuscript for author submission (22 October 2026), under the existing 3000 cumulative physical-attempt and zero-dollar limits. Historical use is 2510. Live regression tests and this extension must both be charged before transport entry under the shared study lock.

Motivation: the versioned Apache Airflow HTTP provider 6.0.0 documentation combines an optional requests adapter, an application response check and an outer tenacity controller. `check_response` changes a returned HTTP error into an exception. This is static source evidence for an integration mechanism, not evidence of deployed retry counts, an Airflow defect or an independently sampled workload. Execute only authored adapters and the already pinned study libraries. No downloaded Airflow code, external APIs or accounts are executed.

The model adds a non-retrying `status_check` boundary corresponding to requests.Response.raise_for_status for HTTP 4xx/5xx. Outer exception eligibility is restricted to the supported adapter classes. Airflow's own exception class is not executed; arbitrary application exception hierarchies remain outside scope.

Freeze 32 cells: GET/POST, four authored scenario families (persistent 503, recovery after two/four 503s, drop then 503 then recovery), and unchecked/checked/single/shared arms. Two executions per cell are stability checks. Outer maximum is three invocations, inner total three retries with default method eligibility, raise_on_status false, no retry sleeps, shared attempt cap four. Timeouts are 0.15/0.08 seconds. No latency or elapsed-bound effectiveness claim is tested. The fixed maximum reservation is 256 physical entries, below the remaining allowance even after 64 reserved live-regression entries.

Before new measurement, store matrix, source hashes, dependency/runtime versions, current cumulative quota and analysis rules in a freeze record. Never overwrite prior raw evidence. Report predictions as conditional persistent-outcome bounds; transient comparisons use explicit scenario replay, not the persistent minimum. Analyze attempts, receipts, successful responses and drained counter effects independently. An effect is the authored server mutation, not an external business transaction. Keep unsuccessful or equivalent baseline results.

Offline implementation validation separately covers a full factorial of method, total counter, raise_on_status, application check, outer attempt limit, exception/result predicates and HTTP status. Its comparator calls actual Retry, Retrying and Response.raise_for_status with sockets disabled; it does not invoke the study simulator. This reduces implementation-commonality risk within the authored finite domain, not sampling or field-validity risk.

After inspection of the four-arm run, add a separate comparator: one tenacity layer capped at four, application status check, and zero urllib3 retries. Evaluate all eight unchanged method/failure conditions with two repetitions, reserving at most 64 entries. This comparator is post-inspection, not independent confirmation. Its purpose is to compare the same four-attempt contract with a strong single-layer baseline; do not claim general superiority from this fixed matrix.
